# MVP 体验打磨需求与技术建议

> 2026-10-28，根据 MVP 试用反馈整理。本文保留打磨前的代码分析与验收规格；本轮实现及实际验证结果见 [cycle-state](cycle-state.md)，原 MVP 验证记录保持历史口径。

## 目标与边界

本文只维护需求、技术依据和验收规格；执行顺序与完成状态统一见 [项目待办](todo.md)。

在已完成的 MVP 上，改善菜谱浏览、详情阅读、冰箱操作、页面导航和清冰箱推荐的体验，并为增加菜谱来源做准备。优先复用现有数据模型、匹配规则和组件，保持 Qt Quick/QML + C++17 架构。

本文记录需求与验收依据；2026-10-28 已按轻量循环完成本轮实现与验证，图片按用户选择延期，外部来源仅静态验证。现有基线见 [PRD v5](../prd-v5.md)、[MVP 需求](mvp-requirements.md) 和 [开发文档](../development.md)。

## 1. 菜谱页面切换与浏览性能

**需求**：进入菜谱页、返回菜谱列表和切换底部标签时，应快速显示可操作的内容。返回列表应保留搜索条件和滚动位置，避免重复等待、闪屏和跳回顶部。

**打磨前实现与可能原因**：

- `app/qml/Main.qml` 的 `showTab()` 每次清空并重建 `StackView`，相同标签重复点击也会重建页面。
- `app/qml/pages/RecipesPage.qml` 使用 `Column + Repeater` 创建全部卡片，并在 QML 中重复过滤 `App.recipes`。
- `app/src/ui/app-model.cpp` 的 `recipes()` 已有缓存，但首次取数仍同步执行全量匹配和摘要转换。上述均为待测量热点，不能据此认定唯一瓶颈。

**技术建议**：

1. 先分别测量首次数据准备、页面创建和首屏显示耗时，区分冷启动、首次进入和再次切换。
2. 菜谱列表改用 `ListView` 按需创建卡片，复用现有 `RecipeCard`；避免在多个绑定中重复过滤同一列表。
3. 由 `Main.qml` 统一管理标签页生命周期和详情栈，按需创建并保留已访问的根页面及其状态。同标签重复点击不重新创建页面，也不重置清冰箱选择。
4. 继续复用 `AppModel` 缓存；按库存、常备品等相关输入的变化使匹配结果失效。细分必要的通知，避免无关操作触发列表重建。
5. 若测量后首次匹配仍阻塞界面，再考虑后台计算；使用不可变输入快照和请求版本校验，不能将现有 SQLite 连接或 UI 对象直接跨线程使用。

**验收**：在固定 Android 设备、相同构建模式及现有 372 道菜的数据集上记录优化前后耗时。建议目标为再次切换至菜谱页 300 ms 内可操作、首次进入 1 s 内可操作；这只是待真机基线确认的目标，不能用桌面结果代替。列表滚动无明显卡顿，返回后保留原状态。

## 2. 菜谱详情的结构化排版与图片

**本轮边界**：按用户选择，本轮只交付文字详情；以下图片能力保留为后续规格，不作为本轮完成条件。

**需求**：详情页应像可阅读、可照做的菜谱，明确区分菜名、简介、用料与用量、操作步骤、注意事项和来源。不得直接堆砌 Markdown 标记。支持封面和步骤图；无可用图片时仍提供完整、整齐的文字版。

**打磨前实现**：`RecipeDetailPage.qml` 已分出用料和步骤，但步骤直接显示字符串；`AppModel::recipeDetail()` 只传递部分字段。`core::Recipe` 已有简介、用量、备注等字段，可优先复用。离线解析器 `tools/whilefresh_tools/recipes/parse.py` 主动移除图片，当前内置数据和 `Recipe` 没有图片字段，因此图片缺失并非只改 QML 即可解决。

**技术建议**：

- 通过 `AppModel::recipeDetail()` 补齐现有字段；QML 继续只承担布局和交互。用料与用量只在对应关系明确时合并，无法可靠对应的保留为独立说明，避免误配。
- 在离线解析器中保留段落、子列表等必要结构，并去除重复编号；页面统一显示步骤序号。正文若采用 Qt Markdown 渲染，应限制为所需格式，不直接渲染第三方任意 HTML。
- 为确有来源的图片增加最小数据字段：图片位置、封面/步骤归属、出处与许可说明；复用同一详情组件展示本地和后续外部来源。相对图片路径应相对于固定版本的源文件解析。
- 文字与图片分别核对可展示范围，优先选少量来源明确的真实菜谱图试点；不以无关配图或生成图充当成品照片。未明确许可的图片不打包、不自动热链。
- 图片按显示尺寸加载、保持比例并延迟加载；加载失败保持版面稳定。缺图不阻塞正文；来源名称和原文入口由数据提供，逐步去掉写死的 HowToCook 文案。

**验收**：普通菜谱、长标题、长用料、多级步骤和备注均可阅读，无原始 Markdown 标记堆积、重复编号、文字截断或重叠。至少用一份来源明确的带图菜谱验证封面/步骤图展示，并验证无图、断网和图片加载失败状态。原用料、用量、步骤与来源不因排版而遗漏或被 AI 改写。

## 3. 冰箱食材行的操作触发范围

**需求**：食材行收起时，点击右侧只能执行正常的行点击行为，不能触发“用掉”“家里没有”等会使食材从当前库存消失的操作。只有明确左滑并展开操作区后，点击实际可见按钮才能执行对应动作。

**打磨前实现**：`app/qml/components/PantryRow.qml` 将操作按钮放在前景卡片背后，但其 `TapHandler` 没有根据展开状态禁用。隐藏按钮仍可能参与事件竞争；应结合实际点击坐标复现确认。

**技术建议**：在现有组件中明确收起、拖动、展开状态。只有越过左滑阈值并结束手势后启用操作区命中；部分露出、动画过程和多选模式下不允许触发库存变更。限制按钮有效区域为已显示区域，处理横滑与纵向滚动的手势竞争。可先修正现有 `DragHandler/TapHandler`，无需为此引入新的手势库。

**验收**：收起时点击行右侧、轻微横移后点击、纵向滚动、右滑标记先用及多选，都不误触发库存移除。左滑展开后按钮可正常执行，收起后立即失效。此项属于防止误操作的高优先级修复。

## 4. 一致的返回导航

**需求**：用户进入详情、编辑或子流程后，必须有位置一致、清晰可见的“返回上一页”入口，并与 Android 系统返回键行为一致。返回后保留上页的选择、搜索和滚动状态。

**打磨前实现**：并非完全没有返回逻辑。`Main.qml` 已有 `goBack()` 和 Back/Escape 快捷键，菜谱详情和部分编辑页也有返回动作；问题是入口与行为不统一，根标签页之间的切换也没有历史语义。

**导航约定与技术建议**：

- 复用 `PageHeader.qml`，统一使用左侧返回入口；由页面发出信号、`Main.qml` 执行导航，避免页面直接操作其他页面。
- 返回顺序为：关闭最上层弹层 → 返回当前标签内的上一层页面 → 返回前一个不同的根标签页。首次所在的冰箱根页无上一页，不显示无效箭头；系统返回沿用退出行为。
- 根标签切换历史仅由用户主动切换记录，返回动作消费历史，不再写回，避免在两个标签之间来回循环。清冰箱的选料、结果和详情应属于明确的流程层级。
- 关闭导入、编辑等流程时沿用已有草稿和取消约定，不让统一返回绕过必要处理。

**验收**：覆盖冰箱→编辑→返回、菜谱列表→详情→返回、清冰箱选料→结果→详情逐级返回、弹层关闭、标签切换历史及系统返回键。可见返回与系统返回到达相同位置，状态不丢失。

## 5. 清冰箱：先选料，确认后展示完整结果

**需求**：清冰箱分为“选择食材”和“查看菜谱结果”两步。勾选、取消只改变本次选择及轻量建议，不在 checklist 下反复重建完整菜谱列表。用户点击“查找菜谱”后，才基于确认的食材集合执行正式检索并进入结果页。

**本轮建议采用的折中交互**：选料时显示已选数量、能覆盖所选食材的候选数量和未找到合适用法的食材提示；不显示完整菜谱卡片或正文。首轮可只显示数量和覆盖提示，无需额外生成自然语言建议。

**当前实现与技术建议**：

- `AppModel::toggleSelected()` 每次清空 `m_clearRecipes` 并发出通用 `changed()`；`ClearFridgePage.qml` 立即读取并用 `Repeater` 展示全部结果。将“编辑中的选择”“轻量建议”“确认后的查询与结果”区分为独立状态和通知。
- 复用 `KitchenService::clearFridge()` 和领域匹配能力，抽取共用的匹配摘要，轻量建议与正式查询必须使用同一套相关性规则。预览只返回计数和覆盖信息，不能为了预览构建完整详情；必要时合并短时间内的连续勾选更新。
- 确认时保存选择快照。后续外部查询只在确认后发起，勾选不触发网络调用；异步返回需校验查询版本，避免旧结果覆盖新选择。
- 返回选料保留勾选；修改选择后正式结果标记为待重新查询，点击确认才替换。默认临期/先用选择仅用于初次初始化或用户主动重置，不因切换标签覆盖手动选择。

**验收**：连续勾选/取消只更新轻量提示，页面不跳动、不出现完整菜谱刷新；未确认时没有外部检索。确认后结果对应当次快照，返回能继续修改。未选食材时按钮不可执行，并给出提示。

## 6. 清冰箱：确保推荐实际消耗目标食材

**需求**：用户主动选择的食材是本次希望消耗的目标。推荐应明确回答“这道菜用到了哪些所选食材，还有哪些没有用到”，不能只因为家中其他食材齐全，就把无关菜谱当成清理结果。

**当前问题的具体依据**：`app/src/core/recipe.cpp` 的 `rankForClearFridge()` 已排除 `selectedUsed == 0`，因此不能简单归因于缺少零命中过滤。当前紫菜蛋花汤数据却把“虾仁（个人口味，可加可不加）”标为 `optional: false`；正文步骤也未使用虾仁。匹配统计同时会计入可选用料，且只要求命中一个所选库存项，蓝莓未用不会阻止这道汤进入结果。

**推荐规则**：

1. 以本次确认的非调料目标食材集合为覆盖分母；重复批次的同类食材按标准食材去重，避免一味食材因多条库存记录获得更高权重。沿用现有词表和有方向的上位关系，不使用字符串包含或臆造替换关系。
2. 只有可靠映射到菜谱必需食用原料的命中，才计入目标覆盖。工具、常备调料、可选配料和装饰性点缀不能单独让菜谱成为清理推荐；不要求每个被选食材都来自肉类或蔬菜，水果也可以是目标食材。
3. 优先展示覆盖全部目标食材的菜谱；没有全部覆盖时，明确提示“未找到同时用到全部所选食材的菜谱”，将只覆盖部分的结果作为单独说明的备选，按覆盖数、缺料数、临期消耗数排序。不要把不合适的蓝莓和虾仁强行组合成一道菜。
4. 每条结果展示“用到：…… / 未用到：……”。零有效命中的菜谱不进入结果；没有有效候选时保留选料并提示调整选择或寻找更多来源。
5. 可选用料仍在详情中如实展示；“是否家里有”和“是否作为本次主要消耗目标”是不同信息，不应混为一个计数。

**技术建议**：在 `RecipeMatcher/RecipeMatch` 中提供有效命中的标准食材集合和覆盖信息，由 `KitchenService` 组织推荐，`AppModel` 输出摘要；QML 不自行计算相关性。修正离线解析器对“可加可不加”等表述的识别，并复核装饰性用料是否需要少量明确标注。先利用已有 `optional/kind/canonical` 字段，只在表达能力确实不足时增加字段。数量是否足以实际做菜仍不在本轮保证范围内。

内置 JSON 必须通过 `tools/` 重建，不能手改生成物；不能只靠上调“命中权重”掩盖数据错误，也不能单凭步骤中未出现同名字符串自动删除原料。

**验收**：蓝莓＋冻虾仁不能把当前这份紫菜蛋花汤作为有效清理推荐；允许出现明确标注“仅用到冻虾仁、未用到蓝莓”的真实虾仁菜谱。另覆盖全部命中、部分命中、零命中、仅可选用料命中、重复库存批次和别名匹配。清理预览、正式结果与详情的命中解释一致。

## 7. 增加菜谱来源：MCP 或第三方 skill

**需求**：下一阶段评估通过菜谱平台接口、MCP 服务或第三方 skill 获取更多真实菜谱，提高食材覆盖率，并补充可展示的图片。接入方式可以替换，产品的食材标准化、推荐、详情展示和缺料清单应持续复用。

**当前状态**：尚未确定平台、服务、skill 或接入权限。已有 [接入调研](../domestic-recipe-grocery-integration-research.md) 记录了 HowToCook MCP、按食材推荐的 skill 及平台限制，结论日期为 2026-10-20；需对选中的候选重新核查，不把第三方封装视为官方接口。

**两条可验证的路径**：

| 路径 | 实现方式 | 适用条件 |
| --- | --- | --- |
| 离线补充数据，优先验证 | 将第三方 skill 作为开发侧检索/整理工具，或复用其可许可的数据处理能力；经过校验后走现有 `tools/ → 内置数据 → BuiltinData/RecipeBook` 链路 | 数据允许本地存储和展示，更新频率不高；手机不需要运行 skill |
| 运行时获取菜谱 | 在应用服务中按需检索，通过适配器把平台 API 或 MCP 响应转换为统一菜谱数据；必要时由受控服务端承担凭据和协议适配 | 已核实接口权限、运行环境、费用、响应时间和内容展示范围；确实需要实时查询 |

**架构约束与验证工作**：

- 先选择一个来源做最小样本验证，不预先建设通用多平台框架。接入第二种运行时来源时，再从现有 `BuiltinData + KitchenService` 调用边界提取最小菜谱提供接口，至少区分搜索摘要与按 ID 取详情；不把网络依赖放进 `core`。
- 所有来源统一到现有 `Recipe` 和词表语义，保留来源、稳定 ID、作者/许可及图片出处；不同来源 ID 应带命名空间。无法可靠映射的用料保留原文并标为未识别，不当成已命中。
- 缓存与持久化遵循 `data` 层边界；QML 仍只访问 `App`，`ui` 层负责加载、取消、超时和结果状态。仅在确定需要运行时联网后再落定网络实现目录，并同步 FHS 与开发文档。
- 外部来源失败时，内置菜谱仍可使用；受许可限制不能缓存全文或图片的来源，仅保留允许的摘要与原文跳转，不承诺应用内全文体验。
- 验证接口可用性、主要食材字段、全文/图片权利、登录要求、移动端适配、延迟和失败行为。代码许可与菜谱内容许可分别核对；MCP 是协议、skill 是工作流，都不能替代数据授权。

**验收**：先提交候选来源与样本验证结论，再决定接入。选中来源的搜索、详情、食材匹配和图片至少贯通一条完整路径，并验证来源失败时的内置回退。不接受只有工具调用成功、无法解释推荐相关性或无法展示来源的集成。

## 架构与验证约束

实施时，领域规则放 `core`，数据解析/存储放离线 `tools` 与 `data`，应用编排放 `KitchenService`，QML 数据接口放 `AppModel`，页面只负责展示与交互。避免为这批打磨另建平行架构。

针对解析与匹配补充上述反例的回归测试；QML 误触、导航、排版与性能按 Android 操作路径验收。修改 C++ 后按项目约定运行 `scripts/build-desktop.sh` 与 `ctest --test-dir build/desktop --output-on-failure`，输出保存到日志；更改 Python 解析器时运行相关测试并按开发文档重建、校验生成数据。外部联网和计费验证另按当次授权执行。

实施与验证证据统一记录在 [cycle-state](cycle-state.md)，当前未完成事项只维护在 [todo](todo.md)。
