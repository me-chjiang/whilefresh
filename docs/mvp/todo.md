## 1. 业务逻辑待对齐（需用户决策）

2026-10-29 对照代码梳理业务逻辑时发现。每项先由用户给结论，再改需求文档或代码。

- [ ] **A1 起算日口径**：PRD / 需求稿写“生产日期 > 购买日期 > 入库日期”；`feat/reliability-data` 未提交改动改为估计天数从购买日起算（无则入库日），生产日期只用于“包装标注 N 天”。改文档还是回退代码（`resolveShelfLife`）。
- [ ] **A2 清冰箱默认选择**：只默认勾“临期 + 先用”，“超出估计期限”不默认勾，是否应一并勾选（`KitchenService::defaultSelection`）。
- [ ] **A3 到期当天状态**：剩余 0 天即判为“超出估计期限”；当天仍算临期还是超出（`FreshnessThresholds`）。
- [ ] **A4 规则与 AI 估计不回溯**：确认的本地规则只影响之后的导入，冰箱已有同类不重算；AI 估计按“标准名 + 存放”永久沿用首次值，无刷新入口。
- [ ] **A5 手填天数压过包装到期日**：代码中单项手填 > 包装标注，文档只写“识别结果最高”。补文档或改优先级。
- [ ] **A6 调料是否跟踪**：识别为调料的商品不进冰箱、不算保质期，只产生“加入常备”建议；词表外调料须选标准名或改为食材才能提交。
- [ ] **A7 清冰箱结果分组**：打磨规格要求“全覆盖优先，部分覆盖单列为备选并说明”；实现为单列表 + 顶部计数。
- [ ] **A8 存量多食材“用掉”无效果**：左滑“用掉”后状态不变，用户可能以为没生效；常备品“家里没有”直接标缺并生成待买建议。
- [ ] **A9 常备品“用完”没有入口**：调料不进冰箱，“我的”只有“移出常备”（= 不再常备，且不进待买）；`KitchenService::markPantryAbsent` 未接 UI。需区分“用完”与“不再常备”。与第 7 节“核对移除常备品的语义”合并处理。
- [ ] **A10 多选“移除”语义**：长按多选后“移除选中”按“家里没有”处理（会标常备缺并生成待买建议），不是“用掉”；是否需要两个动作（`AppModel::removeItems`）。
- [ ] **A11 规则提议触发过宽**：只改购买 / 生产 / 包装到期日期也会问“以后同类都按 N 天吗”，N 为当前算出的总天数（可能来自参考表或包装）；同时改存放和天数时只显示第一个问题（`KitchenService::proposalsForEdit`）。
- [ ] **A12 相对日期确认方式**：需求为取不到截图日期时让用户确认“截图当天”（整张图一次）；实现为逐项填写具体日期，`ImportService::setCaptureDate` 未接 UI。
- [ ] **A13 待买手动添加**：数据模型有“手动”来源、服务有 `addShopping`，但无 UI；需求是否要求。
- [ ] **A14 菜谱用时**：需求“用时只在来源提供时显示”，但 372 道 `time_minutes` 全为空、界面未接；保留还是删除该需求。
