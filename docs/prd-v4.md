# 厨房食材消耗助手 PRD v4

> AI 辅助整理，2026-10-20 根据[完整接入调研](domestic-recipe-grocery-integration-research.md)与[独立能力速查](domestic-integration-brief.md)修订。手机端首版与单人使用由本轮产品方向确定；用户行为、接口申请结果和内容授权仍需验证。

## 产品方向

面向家庭做饭场景，帮助做饭者及时用掉已经买回来的食材，并用有限食材更快决定做什么。**首版是单人手机客户端，手机就是主要操作屏幕**；多人协作是后续方向，不以厨房独立硬件或家庭组为首版前提。

## 需求

家中有人买菜后，食材容易被放进冰箱遗忘。做饭者需要想起哪些食材值得先用，并判断手头有限的食材能做什么。首版聚焦**能取得购物记录、也负责做饭决策的单人用户**；采购者和做饭者分离时如何传递截图，留作用户研究问题。

## 主要矛盾

产品需要知道家里有哪些食材，才能给出有用的消耗建议；但逐项录入、分类和维护库存会额外占用用户注意力。录入越麻烦，信息越容易过时，建议也越不可靠。

购物订单只能证明“买过”，不能证明食材现在仍在家中，也不能推断保质期或食用安全。产品需用少量确认与反馈保持信息可用，避免把推测包装成精确库存。

## 产品原则

- 以消耗食材和完成做饭为中心，不以维护库存为目的。
- 用户不需要先学习库存管理流程，才能获得帮助。
- 优先复用用户主动提供的购物截图和清单；平台 API 只有取得应用权限、用户授权且确认字段后才可接入。
- 菜谱建议须有可追溯来源，不把无来源的 AI 生成内容伪装成真实菜谱。
- AI 可用于匹配食材、筛选和排序菜谱；任何改写或替换建议都应与来源菜谱区分。
- 只提示“值得先看/先用”，不依据购买日期宣称食材即将过期或可安全食用。
- 做饭决策先于补货，缺料清单是完成这顿饭的辅助结果。

## 首版用户路径

1. 用户在手机上从系统相册选取购物订单截图，或在购物 App 截图后从截图预览/相册的系统分享菜单把图片交给本应用。识别商品、数量和可见的购买时间，优先保留食材条目；用户确认、删除误识别项或补充食材后才进入待用列表。相册导入是必须可用的入口，系统分享入口作为首版低打扰路径。
2. 首页呈现少量“现在优先看看”的食材和由此可做的菜。推荐依据已确认的食材、用户主动标记的“先用”以及购买时间等弱信号；购买时间不生成保质期。用户可一键标记“已用掉”或“家里没有”，降低旧记录造成的误导。
3. 菜谱候选显示来源、可用食材、缺少食材；预计用时只有来源可靠时才显示。详情保留原菜谱用料和步骤，AI 的匹配说明、替换建议单独标识。没有足够匹配项时，允许改选主食材或手动补充，而不是编造菜谱。
4. 用户决定做菜后，可把缺料加入按品类整理的待买清单，复制文字或通过系统分享发送给自己/联系人。购物平台内的选品、加购和下单由用户完成；清单不显示未经核实的价格、库存或“一键买齐”承诺。

## 页面与状态

| 页面 | 首版主要内容与动作 |
| --- | --- |
| 今天 | 优先处理的少量食材、匹配菜谱、导入截图入口；无食材时直接显示导入与手动补充入口 |
| 菜谱 | 按现有食材找菜，比较可用/缺少食材；详情展示来源、原步骤和独立的 AI 说明 |
| 待买 | 本次做菜缺料，可删除、复制或系统分享；无缺料时不强迫生成购物清单 |

导入确认是轻量流程，不做常驻“库存管理”页。相册权限、识别失败、重复订单、过时记录和无匹配菜谱均需有可继续操作的状态；用户可删除导入的截图及由其生成的记录。手机界面应便于做饭时单手、短时查看，具体交互尺寸由原型验证。

**数据归属**：首版所有食材线索、菜谱反馈和待买清单属于单人使用空间，不要求创建家庭组。后续若加入多人协作，可扩展为家庭共享空间并定义成员权限与冲突处理；本版不实现邀请、同步或操作日志，也不把所有记录设计成无法区分归属的全局数据。

## 数据与接入边界

- 菜谱首选逐条核实许可和来源的开放文本或自有/授权菜谱；[HowToCook](https://github.com/Anduin2017/HowToCook) 是可评估的数据候选。图片单独核权。匿名可请求的[厨房计划 API](https://proj.kitchen/api/recipes)缺少逐条来源和许可字段，不直接作为正式展示内容库。
- [淘宝买家订单 API](https://open.taobao.com/api.htm?docId=45&docType=2) 有公开定义，但应用权限、买菜订单覆盖未验证，不能成为首版导入前提。其他已查平台没有公开可直接申请的消费者订单/购物车接口；个人信息下载入口的文件内容仍需取样。
- [高德地点搜索 API](https://lbs.amap.com/api/webservice/guide/api-advanced/newpoisearch)可用于“附近门店”候选，需申请 key；没有门店级商品与库存数据时，不显示某店“有货”。附近补货属于后续增强，不阻塞首版做饭闭环。
- 用户可从系统相册选图，也可主动从截图预览/相册的系统分享菜单导入；[iOS 分享扩展](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/Share.html)和 [Android 接收系统分享](https://developer.android.com/develop/ui/compose/sharing/receive)均有官方实现路径。现有[iOS 截图通知](https://developer.apple.com/documentation/uikit/uiapplication/userdidtakescreenshotnotification)与[Android 截图检测 API](https://developer.android.com/about/versions/14/features/screenshot-detection)不支持本应用在后台稳定监测别的购物 App 截图并立即弹自定义窗；自动跨应用弹窗不列为首版交付能力。

## 原型验收与研究指标

- 一位用户可完成截图导入、纠错、找到有来源的菜谱、处理缺料、标记食材已用掉的完整路径；没有真实平台 API 时也能走通。
- 研究记录导入完成率与耗时、每张截图修正项数、建议是否促成做饭决定、菜谱缺料是否准确、数日后记录是否仍可用。先收集基线，再由团队确定达标阈值，不沿用旧版未经验证的留存或减废数字。
- 原型明确展示无食材、无匹配、识别失败、无可用授权菜谱和未知用时/库存的状态，不以虚构数据掩盖限制。

## 明确不做

- 家庭成员协作、家庭组、成员权限和操作日志。
- 完整的库存管理、月度统计、浪费金额和环保贡献报表。
- 在没有来源的情况下让 AI 自行编造菜谱或食材安全结论。
- 自动监控其他 App 截图、跨应用悬浮弹窗、自动读取购物账号或批量代下单。
- 现阶段确定会员、广告、硬件周边、增长方案、开发排期或技术栈。
